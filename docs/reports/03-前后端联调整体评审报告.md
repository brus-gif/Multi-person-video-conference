## 二、模块衔接与协议一致性核验

### 2.1 总体结论
- 分层（UI 控件 / 状态模型 `m_members` / 信令客户端 SC / 服务端 SS / 媒体源）职责清晰、几乎全部对象同属 GUI 线程，**无跨线程与生命周期悬挂类问题**（QObject 父子关系完整，deleteLater 使用正确）。
- 客户端内部"按钮→状态→tile/成员列表"与"网络事件→状态→tile/成员列表"两条路径均最终收敛到同一份 `m_members` 与 tile 状态，方向正确。
- 主要缺陷集中在三类：**①连接生命周期覆盖不全（推流、心跳）②单一状态源被破坏（cam 状态被媒体路径覆盖、说话/点击耦合）③文档-实现-测试三方漂移（回显语义、8MB 上限、ping 建议）**。

### 2.3 文档 ↔ 实现不一致清单（协议层，逐条核验属实）
1. `信令协议.md:53`「建议客户端每 30s 发一次 ping」→ 客户端无任何心跳实现（`SignalingClient::ping()` 无调用方）。→ H1。
2. `信令协议.md:53`「超过 120s 未发任何消息」中"消息"含媒体帧（md:99-103），实现里二进制帧不刷新 `lastActive`（SS.cpp:203-218）。→ H1 服务端半边。
3. `信令协议.md:66-69` 示例中发送者 A 收到自己的 `member_updated` → 实现 `except=client`（SS.cpp:387）；`tst_signalingclient.cpp:149-153` 与 `smoke_test.mjs:100-104` 均按"发送者也收到"断言。→ M2（实现与文档、两份测试矛盾）。
4. `信令协议.md:22`/`protocol.h:12`「set_state 只传变化字段」→ 客户端每次总发 mic+cam 两字段（SC.cpp:83-90，语义兼容但违约）。
5. `信令协议.md:107`「单帧上限 8MB」→ 代码双侧无任何 8MB 校验；服务端注释（SS.cpp:146）自述"默认 1MB 上限"，Qt QWebSocket 是否有该默认需运行验证（待证实 U1）。
6. `room_closed` 表述"主持人离开或房间空"→ 实现仅在 host 离开广播（房空无人可通知，实质等价，无风险）。
7. 信封 `[4B 大端 len][header][payload]`：客户端（SC.cpp:239-271）与服务端（SS.cpp:52-82）**双份实现**，当前逻辑一致，未来易漂移。

### 2.4 静态证实：`signalingtest` / `smoke_test` 在现有服务端实现下预期失败
- 服务端 `handleSetState`（SS.cpp:387）广播 `member_updated` 时排除发送者。
- `tst_signalingclient.cpp:149-153`：A.setState 后 `waitFor(aUpdated>=1 && bUpdated>=1 && cUpdated>=1)` 并断言 `updatedId==selfIdA` —— A 预期收到自己的回显 → **当前实现下 A 收不到，5s 轮询超时，测试失败**。
- `smoke_test.mjs:100-104`：A.waitFor('member_updated') 同样 4s 超时 → **断言失败**。
- 该结论基于源码逻辑推演（本机无法运行验证）。两种可能：实现近期改动未重跑测试，或测试/文档本就陈旧。**无论哪种，都必须统一语义并让三方（文档、实现、测试）一致后重跑。**（备选方案：改为排除发送者并同步改两份测试与文档。）

### 3.1 父 Agent 对子代理报告的纠错（核验记录）

## 四、修改建议（按公共资源归属，供联调排期）

**短期修复清单（按依赖顺序）**

## 六、结论

代码整体结构清晰、模块单一职责与 QObject 生命周期管理良好，宫格算法（gridtest 4/4）与服务端文本信令主干（创建/入会/聊天/离会/关房）逻辑正确。**阻断上线的是三个 P1**：心跳保活缺失（H1）、本机视频默认不推流（H2）、共享时本机宫格被剪影遮蔽（H3）；其次是 P2 中"状态单一事实源被破坏"（M1/M8）与"文档-实现-测试三方漂移"（M2，当前 signalingtest/冒烟测试预期失败）两类系统性问题。建议按 四-1 顺序（服务端 → 信令 → 推流归属 → 状态复位 → 显示解耦）实施，并在可运行环境下重跑 `ctest` 与 `smoke_test.mjs` 后关闭本报告对应条目。
